## 5. Review of migrations, indexes, query plans and transactions

- **Migrations.** Eight forward-only SQL migrations. All apply to an empty MySQL 8.4 schema at the start of every integration and browser run. Migration 007 drops and recreates each guard trigger individually; a guard is absent only between its own DROP and CREATE, so migrations should run with the web process stopped. There are no down migrations.
- **Search query plans** on the 100,000-trip dataset (full plans in [load-test.json](load-test.json)): every step is an index access. `DailyPlan` by service date (const) → published `PlanRevision` (const) → `TripRevision` by revision (ref, about 100 rows for the day) or by departure time (range) → `TripStop` by branch and trip (ref) → `TripStopCategory` by stop and category (eq_ref, FirstMatch). No table scan, and the only filesort is on a single constant row.
- **Indexes.** One missing index was found and added (defect 2). No unused-index analysis was done; that needs production traffic.
- **Transactions.** All 29 service write entry points run through `guardedWrite` (idempotency record, in-transaction authorization, row locks, bounded deadlock retry). No route or page writes outside the service layer; pages and routes only open read transactions for authorization. Outside that pattern by nature: session and rate-limit rows written by the authentication library, and attachment bytes on the file system, which a database transaction cannot roll back.
- **Least privilege.** `SHOW GRANTS` for the rehearsal account: 47 table-level grants per schema: SELECT on the schema, INSERT only on history tables, INSERT and UPDATE on lifecycle tables, DELETE on 13 tables only (three authentication tables and ten master tables). No DDL, TRIGGER or GRANT privilege. Column-level immutability is enforced by the history triggers, not by grants. All five authenticated suites pass with it.

## 6. Load test (measured, single machine)

Dataset (synthetic, schema `moointer_test_run_loade3072a6f07`): 100,000 published trips over 1,000 service dates (100 per day), 500,000 stops, 849,781 stop-category rows, 60 branches; seeded in 300 s. Workload: 35% branch, 20% branch + category + rounds, 17% exact times, 15% loading-time range, 7% alias text, 6% autocomplete; 70% supervisor, 20% department requester, 10% branch receiver; random service date across the whole dataset. Requests went through HTTP to the production build with real sessions and the least-privilege account. The 50 simulated users shared three signed-in sessions (supervisor, department requester, branch receiver), so every request performed a real session lookup, but 50 distinct sessions were not exercised. The load generator, the web process and MySQL shared the one machine.

| Scenario (50 users, 60 s) | Pool | Requests | HTTP 200 | Throughput | p50 | p95 | p99 | Max |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Closed loop, no think time | 5 | 8,271 | 100% | 137.9 req/s | 361 ms | 413 ms | 484 ms | 541 ms |
| Closed loop, no think time | 20 | 7,917 | 100% | 132.0 req/s | 379 ms | 439 ms | 516 ms | 579 ms |
| Paced, about 1 s think time | 5 | 2,951 | 100% | 49.2 req/s | 18 ms | 40 ms | 195 ms | 312 ms |
| Paced, about 1 s think time | 20 | 2,951 | 100% | 49.2 req/s | 19 ms | 35 ms | 213 ms | 350 ms |

Search service alone, without HTTP (274 calls): p50 14 ms, p95 19 ms, p99 26 ms, max 46 ms.

Reading the numbers:

- With 50 users sending requests back to back, the single Node process is the limit (about 135 requests per second); queueing in that process, not the database, makes up most of the 360–440 ms. Raising the pool from 5 to 20 did not help.
- The proposed target was "search p95 ≤ 2 s for 100,000 trips and 50 concurrent users". The measured p95 on this lab was 413–439 ms under continuous load and 35–40 ms with one-second pacing. This is a local baseline. The target itself is still a proposal, was not accepted by the owner, and has not been measured on production-like hardware, over a network, with TLS, or alongside write traffic.
- Not measured: write-path load (planning, receipts, label issue), mixed read/write load, soak tests, datasets beyond 100,000 trips, more than one application process.

## 8. Security review

- **Secrets.** `.env*` and `.local/` are ignored by Git. No current secret value appears in any Git-visible file or captured run log. `.env.example` holds placeholders only.
- **Private files.** Signature-checked uploads stored outside the web root, served only through the authorized route as downloads with `default-src 'none'; sandbox`. No malware scanning.
- **Logging.** Three events (`api.unexpected_error`, `auth.unavailable`, `page.session_unavailable`), each one JSON line with error class, safe code and source location. Verified by a unit test and by the real lines emitted in the database-down check. There is no request log and no log shipping.
- **Sessions.** Database-backed, 8 hours, HttpOnly, SameSite=Lax, Secure when the origin is HTTPS; mutations check the exact Origin. The Secure flag and HSTS could not be exercised without HTTPS.
- **Headers.** `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, COOP, CORP and a same-origin CSP in production builds. The CSP still allows inline scripts and styles (Next.js hydration and the per-page print rule).
- **Open findings** are listed in section 10.

## 9. UI, print and failure states

- **Thai UI and layouts.** Every browser suite runs at 1440, 768 and 390 px and checks for horizontal overflow on search, trip detail, branch directory, planner, masters, consignment form/detail/history, labels and imports.
- **Keyboard.** New keyboard-only test for the search page. Other screens use native controls but were not given a keyboard-only script in this phase.
- **Long text and print.** Long Thai addresses on both label formats, page counts and physical page sizes are measured from generated PDFs. No paper was printed.
- **Failure states exercised:** missing coverage, invalid range, ambiguous and unknown branch, unpublished date, no results, stale version, duplicate submission, over-receipt, invalid upload, invalid import rows, unauthenticated (401), unauthorized (403), unknown page (Thai 404), and database unreachable (Thai 503, sign-in page still renders, liveness still 200).
- **Observed while the database was unreachable:** each affected request waited about 5 seconds for a connection before failing. `GET /api/health/live` does not check the database.
